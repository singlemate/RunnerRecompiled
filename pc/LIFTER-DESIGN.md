# Свой лифтер x86 (PE32) → C → ARM64 для PC-версии Mirror's Edge

2026-11-02. Решение пользователя: только нативный порт, свой лифтер (без pcrecomp/Wine/Box64). Исходные данные — анализ exe GOG в `../PC-PORT-ESTIMATE.md` §7.

## Принципы

- Как XenonRecomp: каждая функция гостя превращается в C-функцию над контекстом CPU. Память гостя — непрерывное 32-битное адресное пространство по базе `mem` (зарезервировано 4 ГБ). Гостевой адрес = смещение от базы.
- В отличие от Xbox, порядок байт x86 и ARM совпадает (little-endian): загрузки и сохранения идут без перестановки байт.
- Exe грузится по своему ImageBase (0x400000) внутри гостевого пространства, поэтому релокации не применяются. Таблица `.reloc` служит только для анализа: по ней видно, какие 32-битные значения являются адресами.
- Дизассемблер — LLVM MC из `libLLVM-23.dll` (llvm-mingw в `work/toolchains`), вызывается через C API (ctypes). Ничего не скачивается. Переходы и вызовы (цели rel8/rel32, `jmp [reg*4+table]`) разбираются по байтам самостоятельно, длину и текст инструкции даёт LLVM.
- Сгенерированный код и все производные игры лежат только в `work/pc-recomp/` и не публикуются. Инструменты лифтера (этот каталог) — код проекта, MIT.

## Этапы

1. **Каталог функций** (`tools/pe32.py`, `tools/x86cfg.py`, `tools/catalog.py`).
   - Затравки: точка входа; цели прямых `call`; обработчики SafeSEH (Load Config); значения из `.reloc` в секциях данных, указывающие в `.text` (vtable, указатели на функции, таблицы областей SEH); импорт-шлюзы.
   - Рекурсивный обход от затравок. Ветвления разбираются по байтам. `jmp` на другую затравку считается хвостовым вызовом. Таблицы `switch` берутся по шаблону `jmp [reg*4+disp32]`: читаются записи, пока на них есть релокация и они указывают в `.text`.
   - Вызовы `noreturn`-импортов (ExitProcess, `_CxxThrowException`, RaiseException, `_exit`, abort, `_invoke_watson`, terminate) завершают блок.
   - Результат: `work/pc-recomp/catalog.json` (функции, блоки, источник затравки) и сводка: число функций, покрытие `.text`, ошибки декодирования, неразобранные косвенные переходы.
2. **Подъём в C** (`tools/lift.py`): регистры, ленивые флаги (результат и операнды последней операции, флаги вычисляются по требованию), x87-стек на `double` (допущение: 80 бит не нужны), SSE на `float`/векторах NEON, строковые инструкции, `lock` как атомики. Прямые вызовы — прямые вызовы C. Косвенные — таблица «адрес гостя → функция» (O(1), массив по `.text`). Неподдержанная инструкция — ловушка с адресом.
3. **Рантайм** (`pc/runtime/`): загрузчик PE в гостевое пространство, TEB/`fs:`, потоки, SEH гостя (цепочка `fs:[0]`, `_except_handler3/4`, `__CxxFrameHandler`), HLE Win32 (KERNEL32/USER32/ADVAPI32/WINMM — по списку импортов), CRT (MSVCR80/MSVCP80: HLE или рекомпиляция DLL — решить после этапа 1), заглушки wxWidgets и dbghelp.
4. **Графика**: COM-объекты D3D9 из `Direct3DCreate9` перенаправляются в DXVK Native (zlib) на Vulkan Android. Шейдеры берутся из `RefShaderCache-PC-D3D-SM3.upk`.
5. **Звук/ввод/видео**: OpenAL Soft (родной), XInput → наш Android-ввод, Bink — HLE или рекомпиляция `binkw32.dll`.
6. **PhysX**: рекомпиляция `PhysXCore.dll` 2.8.x тем же лифтером (у DLL есть релокации) или замена.

```
python -I outputs/mirrors-edge-native/pc/tools/test_x86cfg.py   # 17/17
```

На exe GOG (SHA-256 `58de3df2…60a3dd`):

- **Достижимых функций 178 605**: 157 163 обычных, 19 955 заглушек `__ehhandler` (SafeSEH), 1 487 импорт-шлюзов `jmp [IAT]`. Достижимых инструкций **5,73 млн**.
- Затравки: 42 тыс. из прямых `call`, 107 тыс. из релокаций в данных (vtable, unwind-funclet'ы C++ EH, таблицы нативных функций UnrealScript), 11 тыс. из релокаций в коде, 20 тыс. SafeSEH. Слабые затравки, чей код не декодируется (данные внутри `.text`), отбрасываются: таких 195.
- **Таблицы `switch`: 10 303 записи, все разобраны** (таблицы, общие для нескольких переходов или вложенные одна в другую, перечитываются).
- Ошибок декодирования в достижимом коде нет. Косвенных `jmp reg` 4 679 (`jmp eax/edx`, хвостовые вызовы через регистр): они пойдут через таблицу диспетчеризации, и если цель не является входом функции — ловушка с адресом.
- **Мёртвый код: 49 117 функций, 2,16 МБ.** На них не указывает ни одна релокация и ни один переход из достижимого кода. В exe полная таблица релокаций, значит такой код выполниться не может, и лифтер его не поднимает. Это допущение, см. CHECKLIST п. 35.
- Байты `.text`: код 21,6 МБ (включая мёртвый), таблицы 83 КБ, выравнивание 1,48 МБ, не объяснено 0,47 МБ (2,1 %; в основном данные внутри `.text` и мёртвый код, который сканер не начал с выровненного адреса).
- Набор инструкций достижимого кода: **193 мнемоники, 52 из них покрывают 99 %**. x87 — 3,0 %, SSE — 3,8 %. Редкие: 3DNow! (`pfrcp`), MMX-упаковка, `cpuid`, `daa`, `pushal`, вероятно, ветки по возможностям CPU. Полный список с частотами — `work/pc-recomp/mnemonics.json`, это рабочий список для этапа 2.
- Вывод: `work/pc-recomp/catalog.json` (функции, блоки, хвостовые переходы, флаги, достижимость) и `summary.json`.

Следующее: этап 2 — подъём в C. Начать с функций без x87/SSE и без SEH и сравнивать их с исходным x86-кодом на ПК (дифференциальный тест).

## Результат этапа 2, часть 1: целочисленный лифтер (2026-11-02)

- `tools/lift.py` — x86 → C. Контракт рантайма — `runtime/x86rt.h`: контекст `X86Ctx`, загрузки и сохранения через `X86_MEM_BASE`, ленивые флаги `X86Flags`. Вид операции — константа, поэтому компилятор сворачивает `x86_cc()` до одного сравнения и выбрасывает неиспользуемые флаги. Вызовы — `x86_dispatch`, `x86_import`, `x86_trap`.
  - Регистры живут в локальных переменных C и сбрасываются в `ctx` вокруг вызовов.
  - Прямой `call` кладёт на гостевой стек настоящий адрес возврата и вызывает `f_XXXXXXXX(ctx)`. `ret N` делает `esp += 4 + N; return`.
  - `jmp` на вход другой функции превращается в хвостовой вызов. `switch` по таблице — в C `switch` с `goto`. Косвенные переходы идут через `x86_dispatch`.
  - Блоки функции лифтер находит своим обходом от входа и не опирается на списки блоков из каталога: в каталоге в funclet могли попасть блоки деструктора, найденного позже.
- Охват: **168 175 из 178 605 достижимых функций (94 %) поднимаются целиком.** Остальные упираются в x87 (`st(i)`), SSE (`xmm`, `qword`) и MMX — это часть 2 этапа 2. Полный C — ≈640 МБ исходников (вывод в `work/`, по необходимости).
- Отчёт: `python -I outputs/mirrors-edge-native/pc/tools/lift.py <exe> --llvm <bin> --catalog work/pc-recomp/catalog.json --report work/pc-recomp/lift-report.json`.

### Дифференциальный тест (`harness/`)

- `harness/build_harness.py` отбирает функции, которые лифтер поднял целиком и которые ничего не вызывают и не трогают `fs:`. Генерирует `lifted_tests.c` и собирает 32-битный `harness.exe` (i686-clang из llvm-mingw).
- Стенд запускает себя же приостановленным, резервирует диапазон образа 0x400000 и тестовый буфер 0x30000000 до инициализации процесса, копирует секции exe по родным адресам.
- Каждый случай: случайные регистры, стек и буфер. Значения — указатели в буфер, малые числа, 0 или адреса ≥ 0x80000000, которые всегда дают сбой. Исходная функция вызывается через трамплин (`trampoline.S`), поднятая — как C. Сравниваются 8 регистров, весь буфер и `.data`.
- Сбой (VEH) и зависание (сторожевой поток, 200 мс) прерывают прогон. Тогда вторая версия должна упасть или зависнуть так же.
- `HARNESS_DEBUG=1` печатает регистры каждого случая.
- Запуск: `python -I outputs/mirrors-edge-native/pc/harness/build_harness.py work/pc/Binaries/MirrorsEdge.exe --toolchain work/toolchains/llvm-mingw/llvm-mingw-20261006-ucrt-x86_64 --catalog work/pc-recomp/catalog.json --out work/pc-recomp/harness3k --count 3000 --cases 24 --seed 2`

**Итог на 3 000 случайных листовых функциях × 24 случая:** 55 000 случаев совпали, 16 735 одинаково упали, 30 одинаково зависли. Найдено и исправлено 2 ошибки лифтера: блоки чужой функции внутри funclet и старт C-кода не со входа, когда код лежит ниже входа. Найдена ошибка clang 23.1.3 в i686-генераторе: `(x & 0xFFFFFF00) | zext(load8 [x+k])` компилируется в голый `movzx`. IR верный, x86-64 и AArch64 не затронуты. Обход для стенда — `-mllvm -fast-isel`.

Оставшиеся расхождения объяснены, ошибок лифтера среди них нет:

1. **Мёртвая загрузка** (на -O2, 2 функции). Исходный код падает на чтении, результат которого не используется, а оптимизированный C это чтение выбрасывает. На -O0 расхождения нет. Для работающей игры безразлично (CHECKLIST п. 39).
2. **Входы не через `call`** (14 «функций» из затравок `reloc-code`/`reloc-data`). Это блоки `__except`, обработчики SEH, части таблиц переходов. На стеке нет адреса возврата, и исходный код уходит по `ret` в случайное место. Как с ними обращаться, решит рантайм SEH на этапе 3 (CHECKLIST п. 38).

Следующее (этап 2, часть 2): x87 на `double`, SSE-скаляры и векторы, MMX. Тест тот же, с отбором функций с плавающей точкой и сравнением регистров x87 и XMM.
