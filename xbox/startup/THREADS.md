# Рабочие потоки на Android ARM64 — 21 октября 2026

В реальном AOT-запуске Mirror’s Edge на Y700 созданы два дочерних потока с гостевыми стеками по 32768 байт. Оба действительно начали выполнять XapiThreadStartup 82A09BE0 и дошли до блокирующего ожидания своих событий 00010000 и 00010004. Главный поток продолжил работу и остановился на XGetVideoMode, LR 823AA3A4. Меню и отрисовка не достигнуты. Журнал device-threads-final.log, сводка threads-result.json.

## Реализация

ExCreateThread создаёт настоящий std::thread и независимый PPCContext, гостевой стек, KTHREAD/KPCR и TLS. Дескрипторы потоков отделены от дескрипторов событий. Аргументы передаются через XapiThreadStartup (r3 — пользовательская точка входа, r4 — контекст) либо напрямую (r3 — контекст). Поддержан фактически достигнутый flags=0. Пустой размер стека берётся из XEX, минимальный размер 16 КиБ; тестовый предел 1 МиБ на стек и 16 потоков. Для стеков сохранены некоммитированные соседние области. Host stack и гостевой стек различаются.

PPC-код исполняется под единой блокировкой execution_gate. Она освобождается в ожидании события/потока, спорном входе в критическую секцию и относительной задержке. Другой host thread получает возможность выполнять свой PPCContext. Это кооперативное переключение на границах блокирующих API, а не вытеснение циклов произвольного игрового кода. Цикл без таких вызовов может удерживать выполнение до пятисекундного watchdog. Этот режим пока исследовательский.

Общие метаданные памяти, TLS bitmap и таблицы объектов доступны только под execution_gate. Активный контекст для диагностики, PCR, KTHREAD и адрес TLS сделаны thread_local. FPSCR устанавливается в host thread перед гостевым исполнением. Освобождение TLS-индекса обнуляет соответствующую ячейку во всех зарегистрированных потоках. Память завершённых потоков пока удерживается до выхода процесса.

Критические секции сохраняют рекурсивное владение и гостевой LockCount с учётом ожидающих. При освобождении последнего уровня владельца будится ожидающий поток. События поддерживают реальное блокирующее ожидание, auto/manual reset, нулевой опрос и относительный timeout в 100-нс единицах. NtWaitForSingleObjectEx также ожидает завершение потока. ExTerminateThread завершает только дочерний поток через собственный тип исключения, перехваченный на его host границе; код завершения сохраняется. Завершение начального потока требует отдельной модели жизни процесса и остаётся именованной остановкой.

ObReferenceObjectByHandle возвращает адрес фактического KTHREAD из реестра и учитывает ссылки, ObDereferenceObject снимает их. Проверка типа использует идентичность собственного экспортного ExThreadObjectType; содержимое структуры типа пока не реализовано. Закрытый handle больше не разрешается; записи объектов не переиспользуются. KeSetAffinityThread задаёт маску виртуальных процессоров Xbox и обновляет guest CPU/processor mask; это не назначение физического ядра Android.

KeDelayExecutionThread выполняет реальную относительную задержку, освобождая execution_gate. APC, абсолютные таймауты, system-thread/suspended creation flags, приоритетное вытеснение, повторное использование объектов и полный Xbox object manager ещё отсутствуют. Ограниченные возможности явно диагностируются.

## Проверки

93 проверки прошли непосредственно на Y700: прежние проверки памяти/таймера, запуск дочернего host thread через ExCreateThread, отдельные PCR/stack/TLS, сигнал события из дочернего потока, ожидание общей критической секции, передача владения, завершение через ExTerminateThread с кодом 7 и ожидание thread handle, отсутствие утечки TLS-значений между потоками, очистка TLS во всех потоках, ссылки на KTHREAD, закрытые handles, гостевая affinity, реальный finite timeout и задержка. Журнал device-thread-self-test-final.log. После проверки добавлена только строка журнала object_wait_begin, затем повторён настоящий игровой запуск.

В self-test один элемент таблицы функций временно заменяется собственной синтетической функцией и восстанавливается после завершения дочернего потока. Оригинальные файлы и игровой путь запуска этим не изменяются. Это проверка механики среды, а не доказательство корректности всех многопоточных путей игры.

В игровых запусках реально подтверждены: два создания, два входа в XapiThreadStartup и два ожидания событий. Завершение этих игровых рабочих потоков не достигнуто; их принудительно завершает общий диагностический выход при недостающем XGetVideoMode. Фоновых процессов после проверки не остаётся.
