# Глубина верхнего тайла predicated tiling

2026-10-22. Продолжение XENOS-SAMPLE-POSITIONS.md: силуэты обрываются ровно на строке 512.

## Инструменты

- `prepare_tile_trace.py` — патч RexGlue, все режимы opt-in, по умолчанию поведение не меняется:
  - `ME_DIAGNOSTIC_TILE_TRACE=<кадр>` — копит записи каждого кадра начиная с указанного и печатает первый целый кадр, где есть проход неба `PS 5EBE814012217F48`: каждый draw (окно, scissor, базы EDRAM, depth state, viewport, первая текстура), каждый resolve (copy control, dest, clear) и каждый перенос владения render target (источник, назначение, float32-источник).
  - `ME_DIAGNOSTIC_SKIP_DEPTH_PREPASS=1` и `ME_DIAGNOSTIC_SKIP_TILE_CLEAR=1` — диагностические пропуски draw, не исправления.
- `analyze_tile_trace.py` — раскладывает регистры по полям.
- `work/startup/capture-frames.ps1` — кадры в одинаковые моменты прогона; `dark_stats.py` — доля тёмных пикселей над/под швом.

## Как устроен кадр (кадры 165 и 174)

1. **Depth prepass** всего экрана: 2X MSAA, depth на базе EDRAM 0 (D24FS8), `color mask = 0`, без guest pixel shader, общий VS `BF8AD3FD`, `gequal` + запись (обратный Z), 1280×720 (тайлы 0..1439).
2. **Draw 148:** 4X rect-list с depth `always`+запись и цветом на базах 1024 (D24S8, 7e3). Viewport 1280×720 на 4X-поверхности шириной 640, поэтому адресация EDRAM заворачивается за тайл 2047.
3. **Верхний тайл:** окно (0,0), scissor 0..512, depth на базе 0, цвет на базе 1024. Небо → `DABFFF86` → здания `89670FB6` → `67175986`, тест `gequal` **против глубины prepass**. VS у материалов свои.
4. Resolve цвета в `128E0000`, копия depth и **очистка depth в 0**.
5. **Нижний тайл:** окно (0,−512), scissor 512..720, те же draw, но depth уже очищен — тест проходит всегда.

Так игра и задумана: глубину верхнего тайла никто не «восстанавливает», она просто остаётся в EDRAM после prepass. Нижний тайл prepass не использует.

## Что делает кэш render target на хосте

По журналу переносов: prepass рисует в RT `00688000` (2X D24FS8, база 0). Draw 148 создаёт RT `00308400` (4X **D24S8**, база 1024), и кэш переносит в него владение тайлами 1024..1440, 1440..2048 и **0..1024** (заворот). Перед первым draw верхнего тайла тайлы 0..1024 **возвращаются** из `00308400` обратно в `00688000`, с float32-источником `00688000`. То есть глубина, по которой тестируется верхний тайл, проходит 2X D24FS8 → 4X D24S8 → 2X D24FS8.

## Вывод

Причина силуэтов — порча глубины prepass в тайлах 0..1023 при переносе владения через 4X D24S8 RT, созданный draw 148, и обратно. Шейдеры и позиции сэмплов тут ни при чём: без этого перехода основной проход проходит тест против того же prepass. Опыт с float24 показывает, что при возврате, по крайней мере частично, теряется float32-точность. Но float24 оставляет другие артефакты и исправлением не является.

**Пока не установлено:** что именно портится при переносе — потеря float32 (не совпадает проверка float32-источника), перепутанные сэмплы при отображении 2X↔4X или преобразование float24↔unorm24. Пропуски draw — только диагностика: на реальном Xenos draw 148 тоже стирает часть заворачиваемых тайлов, удалять его нельзя.

## Вид порчи (проба A/B/C)

`prepare_depth_roundtrip_probe.py`, `ME_DIAGNOSTIC_DEPTH_ROUNDTRIP=150`: оба 2X-сэмпла RT `00688000` в точке силуэта (170,450). A — до draw 148, B — после возврата перед небом верхнего тайла, C — после первого draw зданий.

| | сэмпл 0 | сэмпл 1 |
|---|---|---|
| A | `3BCFB86C` | `3BCF8879` |
| B | `3BCFB870` | `3BCF8880` |
| C | = B | = B |

После возврата float32 потерян: значения кратны 8 ulp (мантисса float24) и равны усечению до float24 **плюс 1 младший бит**. В обратном Z это «ближе», поэтому draw зданий не проходит `gequal` (C не изменился).

Механизм (код совпадает с Xenia Canary): перенос D24FS8 → D24S8 пишет float24-биты как unorm через fragment depth в `D24_UNORM_S8_UINT`. При возврате D24S8 → D24FS8 шейдер читает unorm, `RoundEven(x·0xFFFFFF)` и сравнивает с float24 от float32-копии; float32 берётся только при точном совпадении. На драйвере Qualcomm круг через `D24_UNORM` даёт +1, совпадения нет.

Подтверждение: с `ME_DIAGNOSTIC_D32_FOR_D24=1` (guest D24S8 как `D32_SFLOAT_S8_UINT`) A и B совпадают бит в бит (`3BCFB90E`/`3BCF8930`), силуэтов нет.

## Исправление

`rexglue-qualcomm-d24-depth.patch` (render_target_cache.cpp): на `VK_DRIVER_ID_QUALCOMM_PROPRIETARY` guest D24S8 хранится как `D32_SFLOAT_S8_UINT` — штатный путь Xenia для GPU без D24 (например, AMD). cvar `vulkan_depth_unorm24_on_qualcomm` (по умолчанию false) возвращает D24. Патч снят с рабочего дерева: в его контексте есть строки диагностики `ME_DIAGNOSTIC_D32_FOR_D24`; без неё накладывать с `git apply -C1`.

Проверка на Y700 без диагностических переменных: 718 self-tests, exit0 (`work/startup/d24fix-self-test.log`); кадры 35/50 с — 0 % тёмных над и под швом, дальние здания освещены, шва нет (`work/startup/d24fix-50.png`).

Ограничения: Turnip (Mesa) и другие драйверы не проверялись — правило касается только проприетарного драйвера Qualcomm. Цена — 8 байт на сэмпл вместо 4 для guest D24S8 и путь host depth store для них (как на AMD); производительность не измерялась. Чем именно вызвана неточность (запись или чтение D24 unorm), не разделялось.
