# VdSwap: генерация PM4 и продвижение GPU

2026-10-21. Проверено через ADB на Lenovo Y700 test device.

В gpu_bridge.cpp добавлен генератор по закреплённому RexGlue VdSwap: 6 texture fetch words с переводом виртуального адреса в физический, PM4_XE_SWAP с сигнатурой SWAP, адресом и размерами, затем Type2 NOP до 64 слов. Граница bridge использует только числа и массивы, PPCContext ABI не смешиваются. Перед записью проверяются выделение, диапазон команд, texture fetch, формат 6/54, RGB и размеры. Импорт ограничен наблюдённым местом вызова и --gpu-explore. Другие случаи останавливаются. Полный протокол kernel system identifier не реализован, writeback не подделывается.

Игра сформировала блок BF8F1594 для frontbuffer physical 1F558000, 1280x720. VdSetDisplayMode поддерживает только уже выбранный гостевой профиль 0x40000000; параметры экрана Android не меняются.

Первый запуск после этих изменений отправил WPTR 28 и 31, затем завершился диагностическим SIGALRM (20 секунд). Обнаружено ограничение нашего кооперативного исполнения: гостевой busy loop может удерживать execution_gate и лишать GPU времени.

В режиме исследования добавлено окно 10 мс с освобождением gate после записи WPTR. Это диагностическая точка планирования, не вытесняющий планировщик и не гарантия завершения. Доступ к общей памяти остаётся сериализован gate.

Повторный запуск: подтверждено read/write 28/28. После WPTR31 backend начал создавать graphics pipeline с игровым VS hash 1E6883FCCDE1F688. Снимок read/write 28/31; затем SIGALRM при LR827FF5D8. Завершение этого блока, swap, создание готового pipeline и успешный draw не подтверждены. Нельзя интерпретировать запись Creating graphics pipeline как успешную компиляцию.

242 существующих self-tests прошли на обновлённой сборке. Игровые проверки: device-swap-explore.log, device-swap-mode-explore.log, device-swap-yield-explore.log. Регрессии: device-swap-self-test.log.

Следующий шаг: локализовать ожидание внутри обработки второго indirect buffer / создания pipeline и guest polling. Нужна диагностика фактического места остановки GPU, затем полноценные точки планирования и завершение команд; увеличение фиктивных counters не является решением.
