# Оценка перехода на рендер уровня API (как UnleashedRecomp)

2026-10-27. Только исследование: код, сборки, adb и коммиты не трогались. Исходники UnleashedRecomp/XenosRecomp прочитаны через веб (ветка `main` на дату записи; для воспроизводимости ссылки в ANDROID-PORT-RESEARCH.md закреплены на commit). Перекомпилированный код игры в `work/` просмотрен поиском, без цитирования.

## 1. Исходное положение

- Кадр уровня (Stormdrain, ~30 FPS, GPU ≈ 33 мс): сцена и тени ≈ 23 мс, накладные эмуляции ≈ 9,9 мс (resolve_copy 2,6 + edram_dump 2,0 + texture_load 1,9 + host_depth_store 1,8 + copy 1,5), ~140 начал прохода, ~180 барьеров, ~100 dispatch (HANDOFF, профиль `ME_GPU_PASS_PROFILE`).
- `TryResolveCopyDirectly` в RexGlue — заглушка: каждый resolve = дамп host RT в EDRAM-буфер + compute-копия.
- Игра использует **predicated tiling**: 1280×720 с 2X MSAA (цвет + глубина = 2880 EDRAM-тайлов > 2048) рисуется двумя тайлами, верхний scissor 0..512, нижний 512..720, «те же draw» (PREDICATED-TILING-DEPTH.md).
- **Новая находка этой оценки.** RexGlue отвечает на `PM4_EVENT_WRITE_EXT` (screen extents, по ним D3D решает, в какие тайлы попадает draw) фиктивным прямоугольником «весь экран» (`command_processor.cpp`, `ExecutePacketType3_EVENT_WRITE_EXT`, комментарий «Let us hope we can fake this»). Значит, `bin_mask` любого draw пересекается с обоими тайлами, и **вся геометрия сцены отправляется на хост дважды**, отсекает только scissor. Допущение А1: доля геометрии, которая на консоли попала бы только в один тайл, существенна. Это не измерено. Проверка: в tile trace посчитать draw на тайл и долю, у которых проекция лежит целиком в одном тайле.

### 1а. Проверка А1 по существующей трассе (2026-10-28, без планшета)

Трасса `work/startup/tile-trace-decoded.txt` (кадр главного меню/титула, фон с городом, снят 2026-10-22): 259 draw, 1,93 млн индексов. Под predicated tiling идут только **20 draw**: 2X, цвет на базе 1024, сцена неба и зданий. Каждый повторяется во втором тайле (scissor 0..512 и 512..720), это 276 786 индексов на тайл. Дублированная часть — 277 тыс. индексов ≈ **14% всех индексов кадра**. Пиксельная работа почти не дублируется: её уже режет scissor. Остальные проходы (depth prepass 1X/2X, 4X и мелкие пост-эффекты) идут без тайлов.

Вывод: на этом кадре Г4 сэкономит только вершинную работу, порядка 1–2 мс, а не 4–8. Допущение А1 для меню **не подтвердилось**. Для уровня (1036 draw в основной сцене) нужна такая же трасса на Stormdrain: это одна сессия на планшете, `ME_DIAGNOSTIC_TILE_TRACE`. Оценка А8 для полного HLE соответственно снижается: там, где сцена не тайлится, выигрыш даёт только отказ от EDRAM-накладных.

## 2. Как устроен UnleashedRecomp (что именно у них «уровня API»)

Источники: `UnleashedRecomp/gpu/video.cpp` (~290 тыс. символов), README XenosRecomp, README UnleashedRecomp-Android.

- **Перехват.** 42 `GUEST_FUNCTION_HOOK` и 15 `GUEST_FUNCTION_STUB` по жёстким адресам `sub_82BDxxxx…82C0xxxx`: CreateDevice, Present, Get/SetRenderTarget, SetDepthStencilSurface, StretchRect (это resolve), Clear, SetViewport/Scissor, SetTexture, Create/Lock/UnlockTexture, Vertex/IndexBuffer, CreateSurface, Create/Set Vertex/Pixel Shader, VertexDeclaration, SetStreamSource/SetIndices, DrawPrimitive/DrawIndexedPrimitive/DrawPrimitiveUP, D3DX-заливки. Как найдены адреса, в коде не описано: это ручной RE одной сборки игры.
- **Render states.** У XDK D3D `SetRenderState` инлайновый: вызов идёт через таблицу функций в объекте устройства. UnleashedRecomp в `CreateDevice` подменяет эту таблицу своими `SetRenderState<T>` (через `g_memory.InsertFunction`), таблица sampler-state берётся по фиксированному адресу. Состояние хранится в `GuestDevice` (big-endian зеркало структуры XDK) с dirty-флагами. Константы шейдеров читаются из теневых массивов устройства в момент draw.
- **Очередь.** Гостевые вызовы складывают `RenderCommand` в очередь, отдельный render-поток переводит их в plume (абстракция над Vulkan/D3D12). Pipeline кэшируется по XXH64 от `PipelineState`, есть предсобранный кэш PSO.
- **RT / resolve / MSAA.** Каждая гостевая поверхность — отдельная host-текстура с нужным sample count. EDRAM как память не моделируется. StretchRect связывает текстуру-приёмник с поверхностью-источником (`sourceSurface`) и откладывает копию/MSAA-resolve до следующего draw/clear. Resolve делается аппаратно или полноэкранным шейдером (2/4/8X). Predicated tiling в коде не встречается: рендер сразу во весь экран.
- **Шейдеры.** XenosRecomp заранее переводит контейнеры шейдеров из файлов игры в HLSL → DXIL/SPIR-V. На runtime `CreateShader` хеширует microcode (XXH3) и ищет его в отсортированном встроенном кэше. В README: формат контейнера разобран «только для Unleashed», нужна reflection констант. Не реализованы: memexport, mini-vfetch, целочисленные константы, динамическая индексация регистров. Vulkan-locations вершин жёстко прописаны под Unleashed. Автор пишет, что генератор «не такой общий, как хотелось».
- **Текстуры.** Игра хранит DDS-файлы. Хук `MakePictureData` грузит их прямо в host-текстуры, Xbox-формата текстур (tiling, endian) у них почти нет.
- **Специальные хуки движка.** Тени, motion blur, reverse-Z, фейд и т.п. через mid-asm hooks, то есть код, написанный под конкретную игру.
- **Android.** plume/Vulkan, встроенный Turnip (для A830 отдельный драйвер), по умолчанию 50% разрешения, MSAA выкл., AF 4×. Цифра «~12 мс GPU на A830» из основной сессии пришла с этими или неизвестными настройками. Допущение А2: сравнивать её с нашими 33 мс при 100% и 2X MSAA напрямую нельзя.

## 3. Что из этого переносится на Mirror's Edge

| Аспект | Sonic Unleashed (Hedgehog Engine) | Mirror's Edge (UE3, XDK D3D) | Последствие |
|---|---|---|---|
| D3D статически в XEX | да | да: кластер `0x827F2xxx…0x8282Axxx` (~1280 функций, файлы `ppc_recomp.129–133`), рядом `VdSwap`-обёртка `sub_828138E0` и kick `sub_82813450` (GPU-SUBMISSION.md) | искать хуки нужно вручную, как у них |
| Точки входа из кода игры | 42+15 хуков | **186 разных функций** кластера вызываются напрямую из кода вне кластера, всего 788 мест вызова. Самая частая — `sub_827FEB58`, атомарный декремент счётчика ссылок ресурса (`Release`) | объём RE в 3–4 раза больше, чем у Unleashed. Часть из 186 может быть не D3D (XGraphics/XAudio в той же области), допущение А3 |
| PM4 вне D3D | не видно | Type3-заголовки PM4 в коде найдены только в D3D-кластере (DRAW_INDX_2, IM_LOAD_IMMEDIATE, INVALIDATE_STATE, EVENT_WRITE*, WAIT_REG_MEM, REG_RMW, SET_BIN_MASK/SELECT — tiling) **и** в `sub_82E08478/650/830`: SET_STATE (0x25), IM_LOAD (0x27), IM_LOAD_IMMEDIATE. Буфер берётся у аллокатора через косвенный вызов, прямых вызывающих нет (только vtable). Происхождение (D3D precompiled command buffer, XGraphics или UE3) не установлено | **главный риск полного HLE**: где-то пакеты собираются в обход хукаемых функций. Их придётся либо разбирать (то есть всё равно нужен PM4-парсер), либо найти и перехватить API, которое их отправляет |
| Инлайновый D3D | render states через таблицу | то же (XDK того же 2008 г.), плюс инлайновые пути констант шейдеров. Возможны «GPU direct» API (`GpuOwn*`, `BeginCommandBuffer`): допущение А4, не проверено | нужно читать теневые константы устройства на draw, как у Unleashed |
| Текстуры | DDS через свой хук | UE3 cooked Xbox-текстуры: tiled, big-endian, заголовки fetch constant в гостевой памяти. UE3 Xbox RHI, вероятно, создаёт их через XGSetTextureHeader + свою физпамять, без `CreateTexture/Lock` (допущение А5) | хука «загрузить файл в host-текстуру» нет. Нужен кэш по fetch constant + untile + отслеживание записей страниц, то есть **ровно то, что уже делает RexGlue TextureCache** |
| Буферы вершин/индексов | Lock/Unlock | вероятно, тоже свои заголовки поверх физпамяти (А5) | переиспользовать RexGlue SharedMemory + write-watch |
| Шейдеры | контейнеры в файлах, XenosRecomp офлайн | UE3 shader cache внутри пакетов (`*ShaderCache*`), игра передаёт microcode в CreateVertex/PixelShader | XenosRecomp без доработки не подходит. Проще транслировать **тот же microcode RexGlue-транслятором** (уже работает, уже есть диск-кэш пайплайнов, memexport есть) |
| RT, EDRAM-алиасинг | «поверхности с одинаковым описанием делятся» | игра намеренно перекрывает EDRAM: draw 148 4X D24S8 на базе 1024 заворачивается на тайлы 0..1023 глубины prepass (PREDICATED-TILING-DEPTH.md) | модель «поверхность = текстура» ломает такие трюки. Каждое перекрытие надо распознать и смоделировать, отладка картинки заново |
| Predicated tiling | нет | есть (2 тайла) | в HLE это **выигрыш**: рисовать один раз во весь экран |
| MSAA | 2/4/8X host MSAA, можно выключить | 2X сцена + 4X промежуточные цели | host MSAA напрямую или выключение. Выключение MSAA меняет логику UE3, допущение А6 |
| Shading Fix | — | патч кода (меняет инструкции CPU-стороны), к рендеру не привязан | сохраняется как есть. Нужен ли он при HLE — проверить: его причина (мерцание MSAA-пути) может уйти |
| Синхронизация | очередь, fences свои | игра ждёт GPU-фенс (страница 0x1FBF4000), RPTR writeback, VdSwap/interrupt callback 0x82813F58, occlusion queries (EVENT_WRITE_ZPD) | придётся эмулировать фенсы D3D (значения, которые CP пишет через EVENT_WRITE/MEM_WRITE) и запросы видимости |
| Сохранения | — | не затрагиваются: рендер не касается XContent/файлов | — |

Вывод по поиску функций. По сигнатурам найти D3D-функции можно, но вручную: публичных FLIRT-сигнатур XDK D3D нет, по PM4-константам и полям устройства (`device+10941`, `+21532`, таблица render states) кластер выделяется надёжно. Имена функций придётся восстанавливать по поведению (какие PM4/регистры пишет, какие поля трогает). Помогает то, что `GuestDevice` и таблицы из UnleashedRecomp описывают XDK D3D того же поколения: допущение А7, что смещения полей близки, нужно проверить для каждого поля.

## 4. Варианты архитектуры

### Б. Полный HLE D3D (как UnleashedRecomp)

Код игры → хуки D3D (≈60–190 функций) → своё состояние устройства → свой рендер на Vulkan (через plume или напрямую), RexGlue остаётся только как библиотека: TextureCache/untile, SharedMemory, SPIR-V-транслятор microcode, pipeline cache. PM4/CP/EDRAM/RenderTargetCache выключены.

| Подсистема | Объём | Переиспользование |
|---|---|---|
| 0. RE кластера D3D: карта 186 точек входа, структура устройства, таблицы render/sampler state, kick/fence, tiling API; выяснить происхождение `sub_82E08xxx` и ищется ли PM4 в обход | 2–3 нед | GPU-SUBMISSION.md, гостевой трассировщик, GuestDevice из Unleashed как подсказка |
| 1. Модель устройства: render/sampler states, теневые константы (float/bool/loop), fetch constants, viewport/scissor | 2 нед | регистровые декодеры RexGlue (`xenos.h`, `registers`) |
| 2. Поверхности/RT, Clear, Resolve (StretchRect/Resolve → host-копия/текстура-алиас), MSAA, EDRAM-перекрытия, обход tiling | 3–5 нед | идея `sourceSurface` из Unleashed, шейдеры MSAA-resolve |
| 3. Текстуры по fetch constant: untile, endian, форматы, инвалидация по записи | 2–3 нед | почти целиком RexGlue TextureCache + load-шейдеры |
| 4. Вершины/индексы, vertex fetch, DrawPrimitiveUP-аналоги, quad/rect lists | 1–2 нед | RexGlue SharedMemory, PrimitiveProcessor |
| 5. Шейдеры: microcode → SPIR-V через RexGlue-транслятор в режиме host RT, системные константы под новый рендер, диск-кэш | 2–3 нед | SpirvShaderTranslator, кэш пайплайнов |
| 6. Present, VdSwap, vblank/interrupt callback, фенсы D3D, occlusion queries, memexport | 1–2 нед | gpu_bridge, VBLANK-SEMAPHORE.md |
| 7. Отладка картинки до паритета с нынешней (тени, декали, постэффекты, стекло, меню, ролики), A/B с Xenia | 4–8 нед | RenderDoc-процедуры из HANDOFF |
| **Итого** | **17–28 недель (≈4–7 мес.)** при текущем темпе. Реалистично ближе к верхней границе: каждый из шагов 2 и 7 у нас уже занимал недели даже на готовом RexGlue | |

Промежуточные этапы с проверяемым результатом:
1. **Б0 (1–2 нед, без изменения рендера):** гостевые хуки-счётчики на найденных D3D-функциях + сравнение с PM4-потоком. Критерий: каждый DRAW в кольце объясняется вызовом хука. Если нет — полный HLE фактически невозможен без PM4-парсера, остаётся гибрид.
2. **Б1:** «тень» нового рендера рядом с CP: строит свои команды по хукам, но на экран не выводит. Критерий — число draw/RT/resolve на кадр совпадает.
3. **Б2:** главное меню целиком на новом рендере (2D + фон). Критерий — скриншот совпадает с нынешним.
4. **Б3:** пролог/Stormdrain. Критерий — паритет картинки, затем замер FPS и нагрева.

### Г. Гибрид: оставить CP/PM4, убрать дорогие части эмуляции

Те же игровые пакеты, тот же транслятор, правки только в RenderTargetCache/resolve/CP. Каждый пункт независим и измеряется существующим `ME_GPU_PASS_PROFILE`.

| # | Изменение | Объём | Ожидаемая экономия (мс/кадр из 33) | Риск |
|---|---|---|---|---|
| Г1 | Настоящий `TryResolveCopyDirectly`: resolve прямо из host RT без EDRAM-дампа (шейдер копии из image) | 1–2 нед | edram_dump ≈ 2,0, часть copy | средний: форматы/MSAA/частичные прямоугольники |
| Г2 | Resolve → текстура без копии и повторного untile: если приёмник resolve дальше только сэмплируется в том же формате, связать host-image с записью TextureCache (аналог `sourceSurface` Unleashed). Fallback — нынешний путь | 2–3 нед | часть resolve_copy 2,6 + texture_load 1,9 | средний-высокий: CPU-чтение resolve-памяти, частичные resolve, mip |
| Г3 | host_depth_store только когда глубину потом восстанавливают как float32 (учёт времени жизни), вместо нынешних 33 раз/кадр. hds=0 даёт +2–3 FPS, но мерцают декали, значит нужен точный учёт | ~1 нед | до 1,8 | низкий-средний |
| Г4 | **Схлопывание predicated tiling**: (а) дешёвый вариант — честнее отвечать на EVENT_WRITE_EXT (оценка экстентов по viewport/scissor/вершинам или трансформ-фидбэк), чтобы draw одного тайла не шли во второй; (б) сильный вариант — исполнить тайловую последовательность один раз во весь экран с увеличенной моделью EDRAM | (а) 1–2 нед, (б) 3–5 нед | (а) неизвестно, зависит от А1; (б) потенциально 4–8 (основная сцена 7,2 мс, 37 кусков прохода, и её глубинные проходы) | (а) низкий: ошибка экстента = пропавшая геометрия, ловится A/B; (б) высокий: адресация EDRAM 2048 тайлов зашита в RT-кэш и передачи владения |
| Г5 | Меньше разрывов прохода и барьеров: склеивать соседние куски одного RT, батчить barriers | 1–2 нед | 1–3 (оценка, на тайловом GPU) | низкий |

Итого по гибриду: Г1+Г3+Г5 ≈ 3–5 недель, −4…6 мс → кадр ≈ 27–29 мс, **стабильные 30 с запасом**. С Г2 и Г4(а) ещё −3…6 мс → 22–25 мс, около 40 FPS без лимита. Г4(б) — единственный путь гибрида к ≈ 50+, по риску он близок к полному HLE.

## 5. Ожидаемый FPS на Adreno 830

- Текущий путь после Г1–Г5: 35–45 FPS GPU-сторона, лимит 30 ровно. Это реалистично за 1–2 месяца.
- Полный HLE: сцена+тени ≈ 23 мс сейчас включают двойную отправку геометрии из-за tiling и часть разрывов. Однократный рендер во весь экран без EDRAM-накладных — оценка **12–18 мс GPU** при 100% разрешении и 2X MSAA (допущение А8: доля тайлового дублирования ~30–40% сцены). Без MSAA или на 75–50% разрешения — ближе к 10–12 мс, как у Unleashed-Android. Значит 60 FPS по GPU **возможны**, но:
  - CPU-сторона не измерена на уровне: в меню при 60 FPS два потока игры уже ≈100%, большие ядра 91–93 °C. При 60 FPS на уровне упор может уйти в CPU и нагрев. Нужно отдельное измерение (допущение А9).
  - Turnip на A830 вдвое медленнее Qualcomm на нашем потоке. У нового рендера отношение может быть другим.

## 6. Риски (сводно)

1. PM4 вне хукаемых D3D-функций (`sub_82E08xxx`, возможные GPU-direct/precompiled command buffers). Если подтвердится, полный HLE требует PM4-парсера для этих буферов, и выигрыш от ухода от CP частично теряется.
2. EDRAM-перекрытия, на которые UE3 рассчитывает (draw 148), и цепочки resolve → texture → render. В HLE каждую надо найти и смоделировать.
3. Отладка картинки начинается почти с нуля: месяцы уже вложены в паритет с Xenia (D24/D32, sample positions, gamma, тени), и часть этих решений придётся повторить в новом рендере.
4. memexport (вероятная причина отсутствия осколков стекла) — в RexGlue-трансляторе есть, в XenosRecomp нет. При HLE оставлять RexGlue-транслятор.
5. Лицензии: UnleashedRecomp — проверить лицензию перед заимствованием кода. plume — отдельный проект, тоже проверить. Пока заимствуем только идеи.
6. Игровые файлы и сохранения: подход их не затрагивает. Шейдеры транслируются на устройстве из памяти игры, в APK ничего игрового не попадает (как и сейчас).

## 7. Допущения этой оценки (для CHECKLIST)

- А1: тайловое дублирование draw существенно — не измерено.
- А2: «12 мс Unleashed на A830» получено при 50% разрешении/без MSAA или неизвестных настройках.
- А3: все 186 вызываемых функций кластера `0x827F…0x8282` относятся к D3D/Vd — не проверено.
- А4: UE3 может пользоваться GPU-direct API XDK — не проверено.
- А5: UE3 создаёт текстуры/буферы через XGSet*Header на своей физпамяти — по общему знанию о UE3 Xbox RHI, в этом коде не проверено.
- А6: выключение MSAA у UE3 не ломает логику кадра — не проверено (опыт с 75% ScreenPercentage сломал картинку).
- А7: смещения полей `GuestDevice` Unleashed близки к нашему XDK — не проверено.
- А8: доля сцены, которую съедает дублирование тайлов, ~30–40% — оценка.
- А9: CPU-сторона способна дать 60 FPS на уровне — не измерено.

## 8. Вывод: стоит или не стоит

**Полный переход сейчас — не стоит.** Это 4–7 месяцев работы с неустранённым риском (PM4 в обход D3D, EDRAM-перекрытия UE3), повторной отладкой всей картинки и неизмеренным CPU-потолком. Цель «ровные 30» он не приближает: она достигается раньше и дешевле гибридом.

**Стоит**: (1) гибрид Г1 → Г3 → Г5 (3–5 недель, стабильные 30 с запасом); (2) дешёвая проверка Г4(а) и допущения А1 по tile trace — tiling, вероятно, самый крупный «лишний» расход, и он одинаково важен для обоих путей; (3) этап Б0 (1–2 недели, без изменения рендера) как разведка. Если он покажет, что все draw объясняются D3D-хуками, а CPU на уровне тянет 60, к полному HLE имеет смысл вернуться как к отдельному проекту ради 60 FPS.
